# Research Decisions Log

This document records every significant decision made during the data collection and research process for the Political Technology Awards 2026. It is intended to accompany the published dossier so that the methodology is fully transparent and reproducible.

---

## How to read this log

Each entry records:
- **Decision** — what was decided
- **Reasoning** — why
- **Outcome** — what happened as a result
- **Date** — when

## Decisions

---

### 1. Expand scope from 183 shortlisted to all 321 candidates

**Date:** 2026-03-09

**Decision:** Collect enriched data for all 321 projects in `candidates.csv`, not just the 183 that passed the shortlist filter.

**Reasoning:** The shortlist was generated by a 2-of-3-jury rule — projects that appeared in the top greens of at least 2 of the 6 juries. But single-jury greens (projects scored well by one model and missed by others) may be systematically interesting outliers. Enriched data on all 321 makes the full dataset publishable and allows future analysis of what the shortlist filter excluded.

**Outcome:** Collection target set to 321. Output at `cache/enriched/<slug>.json`.

---

### 2. Schema design: align with Civic Tech Field Guide taxonomy

**Date:** 2026-03-09

**Decision:** Use the [Civic Tech Field Guide](https://civictech.guide/) as the reference taxonomy for classifying projects, rather than inventing our own.

**Reasoning:** The CTG represents field consensus — it's the most widely-used directory of civic and political technology, with 311 categories and curated by regional editors. Aligning our schema with it means our classifications are interoperable with existing research and legible to practitioners in the field. Key CTG concepts adopted:
- `project_type` — distinguishes tools from organisations, networks, methods, and campaigns (our existing data conflated these)
- `issue_area` — replaces ad-hoc category strings
- `political_units` (city/state/federal/international) — separates local govtech from global advocacy tools
- `sdg_alignment` — UN SDG tags used by CTG for discoverability
- `communities_served` — who the project actually reaches, not just who it's designed for
- `decade_plus` / `in_civictech_guide` — lightweight legitimacy signals

**Outcome:** Schema defined in `docs/design-enriched-data.md`, Section 1–2.

### 3. Schema additions from v6 jury gap analysis

**Date:** 2026-03-09

**Decision:** Extend the schema with fields specifically targeting the information gaps that caused low-confidence scores in the v6 jury deliberations.

**Reasoning:** Analysis of all six v6 jury delegation files (`iterations/v6/jury-delegations/`) revealed consistent patterns of missing information. All six juries independently hit the same walls:

- **Causation vs. correlation:** Juries couldn't verify whether projects caused the policy outcomes they claimed. AlgorithmWatch's Grok jury: *"timing alone doesn't prove causation."* → Added `causation_strength` (anecdotal / correlated / directly_cited / independently_verified) and `policy_outcomes` as a structured object with links.
- **Failure modes invisible:** Projects only publish successes. The Claude jury gave Awesome Gov Datasets 42% confidence because it couldn't determine what the list excluded or why. → Added `documented_limitations`, `failure_modes`, `jurisdictional_scope`.
- **Governance opacity:** "Open" projects with no public governance criteria are a legitimation risk. Kimi jury on Worker Info Exchange: *"victories remain legally bounded to UK/EU jurisdictions."* → Added `curation_criteria`, `contributor_governance`, `disparity_tracking`.
- **Research claims unverifiable:** The experimental lens juries (Grok, Kimi, Specialist) consistently noted that research claims without replication packages cannot be independently verified. → Added `replication_materials_available`, `preregistered_studies`, `published_performance_metrics`.
- **Funding unverifiable:** Funding claims on homepages are unaudited. → Added `funding_verified` (cross-referenced against Form 990, EU grants, OpenCharities) and `last_funding_event`.

**Outcome:** Schema extended to 10 sections. Full rationale in `docs/design-enriched-data.md`.

### 4. Collection pass architecture: three passes

**Date:** 2026-03-09

**Decision:** Structure data collection as three sequential passes, each targeting a different depth of research.

**Reasoning:** A single deep-research pass for 321 projects would be slow and inconsistent. Separating by depth allows fast broad coverage first, then targeted gap-filling.

**Pass 1 — Broad sweep:**
Sources: project homepage, About/Team pages, general news search, Wikipedia, GitHub, civictech.guide.
Goal: populate core fields for every project.

**Pass 2 — Null field targeting:**
Trigger: any file with 10+ null/empty fields after pass 1.
Sources: field-specific searches (news by outlet, funders via annual reports, elections, AI involvement).
Goal: close the most common gaps with more targeted queries.

**Pass 3 — Structured database lookups:**
Sources: ProPublica Nonprofit Explorer (Form 990s), EU CORDIS (Horizon Europe grants), OpenCharities/Charity Commission (UK), GitHub API (stars, forks, contributors, commit frequency), OpenAlex API (academic citations, paper counts), Knight/Ford/OSF grant databases, NDI/Carter Center election reports.
Goal: replace self-reported or inferred data with verifiable structured records.

**Outcome:** Three parallel agent streams running. Progress tracked via `ls cache/enriched/ | wc -l`.

### 5. WebFetch banned for bulk research

**Date:** 2026-03-09

**Decision:** All bulk web fetching uses `curl --max-time 20` via Bash. `WebFetch` is prohibited in research loops.

**Reasoning:** `WebFetch` is a built-in Claude Code tool with no configurable timeout. A single slow or unresponsive site caused a subagent to hang for 26+ minutes, blocking its entire batch. `curl --max-time 20` provides a hard OS-level kill after 20 seconds with clean failure.

**Outcome:** Documented in Xiao Mei's `CLAUDE.md` under `## Web Fetching During Research`. All subsequent subagents use curl.

### 6. Container timeout disabled for discord_main

**Date:** 2026-03-09

**Decision:** Set `timeout: 0` in `registered_groups.container_config` for `discord_main`, disabling the container kill timer entirely.

**Reasoning:** The previous 30-minute activity-reset timeout made sense for chat (keeps idle containers from consuming resources) but is wrong for long research tasks where the agent may legitimately need hours. The timeout was originally a safety net for zombie containers; for a trusted long-running research agent it creates unnecessary risk of mid-task termination.

**Outcome:** `container-runner.ts` updated to treat `timeout: 0` as "no timeout". Container runs until the agent exits naturally. Change is per-group — all other groups retain the default 30-minute timeout.

---

### 7. Parallel agent batch size: 90

**Date:** 2026-03-09

**Decision:** Default parallel subagent batch size set to 90 simultaneous background agents.

**Reasoning:** Initial collection was running 3–4 agents at a time, producing ~4 projects/hour against a 321-project target. The Anthropic API allows 3,000 requests/minute — no rate-limit reason to self-throttle. VPS has 6.2GB available memory; each subagent consumes ~100–200MB, so 90 concurrent is well within headroom. 90 was chosen as a practical ceiling below the full 321 to avoid scheduler contention on a 2-CPU VPS.

**Outcome:** Documented in Xiao Mei's `CLAUDE.md` under `## Parallel Agent Tasks`. Each subagent writes its own output file directly to disk and returns a one-line status — coordinator never aggregates large payloads, avoiding context window exhaustion.

### 8. Output location: data/enriched/

**Date:** 2026-03-09

**Decision:** Store enriched JSON files at `data/enriched/<slug>.json`.

**Reasoning:** `data/` is the semantically correct location — it separates human-curated research data from pipeline-generated `cache/` outputs. Early collection used `cache/enriched/` as a workaround because `data/` didn't exist yet and the container lacked write permission. Once `data/` was created with `o+rwx` permissions on the host, all files were migrated and the path standardised.

**Outcome:** `data/enriched/` created, world-writable from container. 67 files migrated from `cache/enriched/`. All subsequent passes write to `data/enriched/`.
